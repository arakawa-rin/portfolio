制作物紹介

旅行やイベントで発生する支出を記録し、参加者ごとの負担額と精算額を整理するアプリ PayLog について、設計意図と実装上の工夫をまとめています。

info アプリの概要

アプリ名

PayLog（ペイログ）

概要

イベントや旅行などの支出を記録し、参加者間の精算を簡単に行えるアプリです。

課題

会計係に負担が集中する

旅行やサークルイベントでは、参加人数が増えるほど支出管理や精算計算が複雑になります。ゼミ合宿では、会計係がPCを持参してExcelで管理し、後から金額修正が発生することもありました。

↓
PayLogでの解決

支出登録と自動精算で手計算を減らす

支出・参加者・支払者をアプリ上で登録し、精算結果を自動で計算できるようにしました。会計係の手作業や計算ミスによる修正の負担を減らします。

イベント作成 参加者管理 支出登録 自動精算
課題

傾斜割り勘がしづらい

飲み会やイベントでは、お酒を飲まない人、運転を担当する人、幹事など、負担に差がある場面があります。しかし、細かく計算するのが面倒で、一律の割り勘になりやすい課題があります。

↓
PayLogでの解決

口数割で負担差を反映する

一律割り勘だけでなく、参加者ごとに負担割合を変えられる口数割に対応しました。負担差を考慮した精算を、手計算なしで行えるようにします。

均等割り 口数割 負担割合設定 自動割当計算
課題

立替を請求しづらい

旅行やイベントでは、誰かが一時的に多く立て替える場面があります。精算が複雑になるほど言い出しづらくなり、遠慮しがちな人や気前の良い人がそのまま負担してしまうことがあります。

↓
PayLogでの解決

誰が誰にいくら払うかを自動表示する

参加者ごとの支払額・負担額をもとに、誰が誰にいくら支払うべきかを自動で整理します。口頭での請求に頼らず、アプリ上で精算結果を確認できます。

立替管理 負担額計算 精算結果表示 送金ペア算出

photo_library Paylogの使い方とスクリーンショット

イベントを作成して、招待コードで参加し、支出を追加して精算結果を確認するまでの流れを実際の画面遷移に沿って並べています。

1

イベント作成

旅行やイベント名、参加者、日付を登録して、精算の単位になるイベントを作ります。

2

イベント一覧

作成済みのイベントを一覧から選び、支出の追加や精算確認へ進みます。

3

イベント詳細

参加者と最近の支出を確認しながら、必要に応じて支出追加や精算へ移動します。

4

支出を追加

支払った金額や費目を入れ、使う場面に合わせて割り勘モードか口数割モードを選びます。

splitscreen

割り勘モード

立替人と負担者を選ぶだけで、一律の割り勘をすばやく登録できます。

calculate

口数割モード

1口単価と参加者ごとの口数を入力し、合計や過不足を見ながら傾斜のある負担額を決められます。

5

精算結果

参加者ごとの負担額と立替額をもとに、誰が誰へいくら支払うかを確認します。

6

招待コードで参加

イベント詳細画面に表示される招待コードを入力すると、ほかの参加者も同じイベント詳細画面に入れます。参加後は支出の追加や編集を共同で行えます。

layers 使用技術

Frontend

React Native / Expo / TypeScript を中心に、iOS 前提の画面を構築しています。 Expo Web と react-native-web により、同じUIをWeb体験版としても公開できる構成です。

Backend

Flask / Flask-SQLAlchemy で REST API を実装しています。 イベント、参加者、支出、精算をAPI単位で分け、入力チェックや権限確認をサーバー側でも行っています。

Database

Supabase の PostgreSQL を利用する想定です。 SQLAlchemy のモデルでは、参加者・支出・負担配分を分けて管理し、精算計算に必要なデータを正規化しています。

Infrastructure / Deployment

Render 上で gunicorn により Flask アプリを起動し、Expo Web の dist を Flask から配信します。 本番では同一オリジン、ローカルでは CORS を許可する構成にしています。

architecture アーキテクチャ図

iOSアプリとしての利用を軸にしつつ、Web体験版を同じバックエンドに接続する構成です。 本番では Render が静的ファイルとAPIをまとめて配信します。

schema ER図・DB設計の意図

DBは、イベントそのもの、イベント内の参加者、支出、支出ごとの負担配分を分けて管理しています。 支出テーブルに全員分の負担を直接持たせず、Allocations に分離することで、均等割と口数割の両方を同じ精算ロジックで扱えるようにしています。

users events event_participants expense_categories expenses allocations settlements

現状はゲスト利用を前提にしながら、users と event_participants を分けているため、 将来的にログイン機能を追加しても、イベント内での表示名や参加状態を独立して扱いやすい構成です。 deleted_at や status、joined_at / left_at もあり、削除・退室・再参加の状態管理を拡張しやすくしています。

Frontend

design_services フロントエンドで工夫した点

最下部ナビで、迷わず移動できる導線にした

イベント一覧、作成、設定という主要な操作を最下部に固定し、中央の作成導線を強調することで、初見でも移動先を直感的に判断しやすい構成にしています。

多くの人が日常的に使っているSNSアプリでも最下部ナビが採用されているため、 PayLog でも同じUIを取り入れ、画面を開いた瞬間に「どこへ移動できるか」が伝わることを優先しました。

口数割の入力途中でも、金額の一致・不足・超過が見えるようにした

支出追加画面では、割り勘方式の切り替えに応じて入力項目を出し分け、口数割ではその場で合計と差分を表示しています。

金額と1口単価、口数の関係を見える化しているため、複雑な割り方でも入力の迷いを減らせます。

一覧を折りたたみ・検索・並び替えで整理し、モバイルでも情報量を制御した

イベント詳細では参加者と支出を一定件数で折りたたみ、支出一覧には検索とソートを入れて視線移動を減らしています。

Web体験版でも破綻しにくいよう、一覧の密度を抑えつつ操作軸を明確にしています。

Backend

build バックエンドで工夫した点

精算結果を正しく返すだけでなく、送金関係の整理、金額処理の信頼性、 仕様変更への追従しやすさまで含めて設計しています。

送金関係を整理する精算ロジック

参加者ごとの収支差額から債権者と債務者を分け、差額が解消される組み合わせを順に作ることで、 複数人の立替が混在しても送金関係を追いやすい精算一覧に変換しています。

送金回数をむやみに増やさず、最終的に「誰が誰へ支払うか」が一目で分かる形へ整えることを重視した実装です。 

creditors.sort(key=lambda x: x["net"], reverse=True)
debtors.sort(key=lambda x: x["net"])

while creditors and debtors:
    creditor = creditors[0]
    debtor = debtors[0]

    settlement_amount = min(creditor["net"], -debtor["net"])
    settlements.append({
        "payee_display_name": creditor["display_name"],
        "payer_display_name": debtor["display_name"],
        "amount": settlement_amount
    })

    creditor["net"] -= settlement_amount
    debtor["net"] += settlement_amount

    if creditor["net"] == Decimal('0'):
        creditors.pop(0)
    if debtor["net"] == Decimal('0'):
        debtors.pop(0)

差額の大きい組み合わせから順に解消していくことで、複雑な立替関係をそのまま精算フローへ落とし込んでいます。

1円単位の信頼性を支える金額処理

支出額、負担額、精算額の計算を Decimal ベースで揃え、1円単位のズレが精算結果に波及しにくいようにしています。

現在は円表示が中心ですが、将来的に通貨や丸め要件が増えた場合も、数値型の前提を崩さずに拡張しやすい構成です。 

decimals = [Decimal(value) for value in values]
floored = [
    int(value.quantize(Decimal('1'), rounding=ROUND_DOWN))
    for value in decimals
]
target_total = int(
    sum(decimals, Decimal('0')).quantize(Decimal('1'), rounding=ROUND_HALF_UP)
)
diff = target_total - sum(floored)

allocate_integer_values で実際に使っている抜粋です。Decimal を前提に丸め方まで固定しているため、表示時の整数化でも扱いがぶれません。

変更に強い責務分離設計

支出登録時の入力検証は validate_expense_input、均等割と口数割の配分は create_allocations、 精算結果の計算は api_settlements と build_integer_settlement_result に分けています。

たとえば割り方の仕様が増えても、配分ロジックを中心に見直せばよく、入力チェックや精算表示まで巻き込みにくい構成です。 

validated, err = validate_expense_input(data, event, event_id)
if err:
    return jsonify({"success": False, "error": err}), 400

alloc_error = create_allocations(
    expenses.expense_id, event_id, expense_amount,
    split_method, participants_ids, data
)

integer_summary, integer_settlements =
    build_integer_settlement_result(settlement_summary)

1つのAPI内でも処理を役割ごとに呼び分けており、仕様変更時に確認すべき箇所が絞りやすくなっています。
